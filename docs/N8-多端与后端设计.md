## 1. 三句话目标

1. **一套核心**：`src/` 保持零构建 / 零依赖 / 双击能跑（**不变**），它是唯一一份游戏逻辑。
2. **一层适配**：所有端差异**只允许**出现在 `G.Platform`（已有 8 组能力 + 新增 1 组 `net`）。
3. **一个后端**：所有端共用同一份服务端；**一期只做 L1（非社交）**，不做好友 / 聊天 / UGC。

⛔ **不做什么**：不做两份代码库、不做「编译期分叉」（`if (TARGET === 'wx')` 撒进业务代码）。

## 3. 身份模型（最关键的一处设计）

**规则：主键永远不是任何端的私有 ID。**

```
account (后端主键，自己生成 uuid)
  ├─ identity: { provider: 'local',  providerUid: <本机 uid> }      ← 现有 profile.js 的 uid
  ├─ identity: { provider: 'email',  providerUid: <邮箱> }
  ├─ identity: { provider: 'steam',  providerUid: <SteamID64> }     ← 后置
  └─ identity: { provider: 'wechat', providerUid: <openid> }        ← 后置
```

- **`local` 身份先存在、永远存在**：不登录也能玩（离线），登录只是**把本机账号绑到一个 account 上**。
- **绑定而不是替换**：绑定后本机 `uid` 仍然有效（它只是 account 的一个 identity），
  这样「退出登录 / 换设备 / 断网」都不会让玩家丢档。
- ⛔ **不许**把 `openid` / `SteamID64` / 邮箱当主键 —— 那样 Steam 端接进来时要改数据模型（= 返工）。
- **冲突合并（首次绑定云端时）**：可能「本机有进度」+「云端有进度」。
  ✅ 规则：**不自动合并**，给玩家二选一（「用本机进度覆盖云端」/「用云端进度覆盖本机」），
  并把**被覆盖的那份另存为 `.rescue`**（复用 `state.js` 已有的兜底键）。
  ⛔ 别做「字段级自动 merge」—— 那会造出两个都不成立的中间态（本项目最忌的「同一个事实两份真相」）。

**接口草案**（只定形状，不定实现；路径前缀 `/api/v1`）：

```
POST /auth/anonymous        → { deviceToken }                 # 先给匿名身份，不强制登录
POST /auth/bind             → { provider, credential }         # 绑邮箱 / 后置 steam、wechat
POST /save/pull             → { rev, payload, updatedAt }
POST /save/push             ← { rev, payload }  → { rev }      # 乐观锁：rev 对不上就要求二选一
POST /telemetry             ← { events: [...] }               # 匿名、不含身份
GET  /assets/manifest       → { sizes, files, expires }
```

## 5. 存档与同步（**本地优先**，云端是备份不是真相）

1. **本地永远是能玩的**：所有逻辑继续读本地存档；云端不可达时**静默跳过**同步（不报错、不阻塞）。
2. **存档比较用「单调递增的 rev」**，不用时间戳（设备时钟不可信、会造出「未来存档」）。
3. **上传时机**：关键节点（钓到新鱼 / 卖出 / 关页面 / 每 N 分钟节流），复用 `state.js` 现有 `save()` 的节流思路。
4. **下载时机**：启动时 `pull` 一次；`rev` 与本地相同就什么都不做（幂等）。
5. ⚠️ **与 Steam Cloud 二选一**：Steam 自带云存档，和自建云存档**同时开一定会打架**
   ⇒ Steam 版建议**只用 Steam Cloud**（把 `net` 的存档同步能力置空），小游戏 / 网页端用自建。
   ⇒ 这条要写进 `Platform.net` 的能力语义里（「有没有云端存档」由平台层回答，业务侧不判断端）。

## 6. 资源托管与 size 档

- **目录**：新目录 `assets/cards-ui/`（**与 `assets/cards/` 原始母版分开**）—— 见 `docs/改进待办.md` 的 **Q8**。
- **`manifest.json` 加一维**：每个档位记 `{ size: { sm, hd }, w, h, bytes, hash }`；
  **小游戏吃 `sm`（低码率）、Steam 吃 `hd`（高清）** ⇒ 「精美程度」不用靠分叉代码。
- **游戏侧只按 manifest 曝光**：接触表判 `ok` 的档位才给游戏侧（= 队列里的 **N3-2**），
  ⚠️ 用 manifest 自己的标记，**不另建第二份真相**。
- **小游戏侧**：主包只放代码（≤4MB），卡面**全部走远端** + 分包；⚠️ **所有请求域名必须 HTTPS + ICP 备案 + 平台白名单**。
- **Steam 侧**：卡面可以随包（但要考虑下载体积）或首次启动按需下载；
  ⚠️ **`file://` 下 `fetch` 被拦**是**已实测**的坑（N3-1 那轮踩过）⇒ Electron 版**不能靠 `file://` 取素材**。

## 7. Electron 套壳（Steam 版怎么发）

**为什么必须做**：Steam 官方口径 —— **不接受网页 / 浏览器游戏，必须有原生桌面可执行文件（Windows .exe 最低要求）**。

- **位置**：新目录（建议 `shell/`），**不进 `src/`**。
  🔴 **零依赖硬约束的边界**：`src/` 仍然零依赖；**依赖只允许出现在外壳与工具链**里（这跟 `tools/` 用 Python 是同一个道理）。
- **形态**：Electron 主进程 + 一个 `BrowserWindow`，加载 `tools/build.js` 产出的单文件 HTML（或本地静态目录）。
- ⚠️ **关键坑（已实测同类）**：`file://` 下 `fetch` 被拦、画布贴本地图会被标记**被污染**（`getImageData` 抛 `SecurityError`）
  ⇒ Electron 里**不要用 `file://` 加载**，改用 `app://` 自定义协议或本地 http 服务。
- **打包**：`electron-builder` 一类（产物 ≈ 100~200MB —— 这跟「双击即玩」无关，后者只是开发期形态）。
- **Steamworks 集成（可选、后置）**：成就 / 云存档 / 覆盖层。⚠️ 它**会引入 node 原生依赖** ⇒ 只许待在外壳进程里，
  通过 IPC 暴露给页面（`G.Platform` 加一个 `steam` 能力组，**由外壳提供实现**）。
- **商店素材是硬门槛**（并行准备，别等代码）：多尺寸 capsule（**画面里必须含游戏标题文字**）+ ≥5 张截图 + 预告片。
- ⚠️ **别开国区 / 别做国内充值链路**（灰区，风险自担）。

## 8. 一期范围与验收

**做**：本文档（数据模型 + 能力目录 + 接口草案 + 端差异清单）。
**不做**：任何代码、任何云资源、任何端适配实现。
**验收（本文档算通过的标准）**：
1. 身份模型能回答「Steam 端接入时要不要改数据模型」→ **不用改**（主键与端无关）。
2. 端差异清单能回答「新功能写在哪儿」→ **业务代码不出现任何端名**（`wx` / `steam` / `electron` 都不许进 `src/`）。
3. 存档方案能回答「离线能不能玩」→ **能**（云端不可达 = 静默跳过）。
4. 资源方案能回答「1.5GB 怎么发」→ **远端 + size 档 + manifest 曝光**。

## 9. 风险与待确认

| # | 风险 | 处理 |
|---|---|---|
| 1 | **排行榜**算不算「社交系统」（触发版号） | ⚠️ **向渠道 / 出版单位确认后再做**；一期不做 |
| 2 | Steam Cloud 与自建云存档**打架** | 二选一（Steam 版用 Steam Cloud），写进 `Platform.net` 语义 |
| 3 | 小游戏**域名 ICP 备案**是排期瓶颈（数周，且换域名要重走） | 提前办；选支持固定域名的 CDN |
| 4 | Electron 让包体从 0.6MB 变成 100MB+ | 只在 Steam 版发生；网页 / 小游戏端不受影响 |
| 5 | 后端一旦上线就有**运维与成本**（选型见下） | 首选**托管 BaaS**（快 / 无运维 / **可逆**），自建留到确有需要 |
| 6 | 自建云存档 = 玩家数据在你手上 | 最小化收集；只存存档 + 匿名统计，**不存密码明文**（沿用 `profile.js` 的派生口径） |
| 7 | 「一套核心」被慢慢侵蚀（有人图省事在业务里判端） | `verify ㊱` 的字面量白名单继续守；新增能力必须走 `G.Platform` |

**待用户拍板（只剩 2 条，其余已定）**：
1. **后端形态**：托管 BaaS（推荐）vs 自建。
2. **是否现在就做 Electron 外壳**（它决定 Steam 版能不能进排期；不做则 Steam 只能等）。
