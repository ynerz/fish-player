# 每小时优化轮次规范

> **适用**：`钓鱼人生 · 持续优化改进`（每小时跑一次的自动化，工作目录 `D:\fish player`）。
> **由来**：用户口径（2026-10-08）——
> 「将每次的修改规范确认，我每个小时都会运行一遍程序进行优化，安排的工作内容不宜过少，
> 如果上个还没优化完，在规范里说跳过这次优化即可，**但是要仔细检查是否真的影响这次优化**。」
> **配套文件**：`docs/优化队列.md`（派单表 + 轮次台账）。**每轮开工先读它，收工必须更新它。**
> **不重复内容**：条目正文一律以 `docs/改进待办.md` 为准；队列只排序，不复制。
> 本文与 `docs/开发者文档.md` §18（每轮收尾清单）是**互补**关系：§18 管「改完怎么收尾」，
> 本文管「一轮从开工到交接怎么走」。

---

## 0. 一句话

每轮 = **看清工作区 → 选一个条目 → 做完做实 → 门禁双绿 → 写台账与文档 → 一笔提交**。
做不到「做完做实」就别开第二个条目；**但也不许把一轮做空**（见 §3）。

---

## 1. 开工前（约 3 分钟，一步都不许跳）

1. `git log --oneline -6` + `git status --short`
   → **先看清工作区是谁弄脏的**。别把后台生图 / 用户手改 / 上一轮的半成品当成自己的改动。
2. 读 `docs/优化队列.md` 的 **§1 当前状态**（上一轮的交接）与 **§2 派单表**。
3. 跑门禁：

   ```bash
   node tools/test.js && node tools/verify.js
   ```

   - **门禁红 ⇒ 本轮先修门禁**，不接新条目（这是唯一优先级高于「做队列条目」的事）。
   - 门禁绿但工作区脏 ⇒ 按 §4 判脏源。
4. 看后台在不在生图：`ls assets/cards/.gen-art.lock`
   → **在跑就本轮避开 `tools/gen-art.py` 与 `assets/cards/`**（见 §4 与队列里的阻塞标记）。

---

## 2. 选条目

- 从 `docs/优化队列.md` **按顺序**取第一个**可做**的条目。
  「可做」= 未阻塞 **且** 不与在跑的任务冲突 **且** 不需要用户拍板。
- 队列条目**必须**在 `docs/改进待办.md` 里有对应正文。**队列里不写正文**（写两份必然分家）。
- 队列里的条目**全部不可做**时：
  ① 按 §3 的 **C 类**做一次只读审计；
  ② **必须给队列补新条目** —— 把审计发现的问题追加进 `docs/改进待办.md`，再联进队列。
  ⚠️ 「没活干」不是允许的状态：这个项目从来不缺已知问题。

---

## 3. 工作量下限（用户点名「不宜过少」的硬线）

一轮的产出**至少**满足下面任意一条，否则这一轮**不算完成**：

| 类型 | 要求 | 备注 |
|---|---|---|
| **A 类** | 完成 1 个队列条目，改动落在**代码 / 数据 / 工具**上，并有可执行的验证留痕 | 纯文档、纯注释、纯改名**不算** |
| **B 类** | 完成 **3 个以上同类小修**（可合并成一笔提交） | 例如一轮清掉 4 处文档漂移 |
| **C 类** | 只读审计：产出**可复现的结论**（写清命令、口径、结论、反例），并把新发现追加进待办并联进队列 | ⚠️ **不许连续两轮**；上轮是 C 类 ⇒ 本轮必须是 A 或 B |

**同时设上限**：一轮**最多** 1 个 A 类条目（外加若干 B 类小修）。
贪多会让「做完做实」和「一笔提交一个条目」同时破功 —— 比做少更糟。

**划水自检问句**（答不出来就说明这轮在白跑）：

> 「用户打开游戏、或看一份产物，能不能**看出 / 听出**这轮做了什么？」

答「改了注释」「更整齐了」「补了文档」→ 不成立，回去重选条目。

---

## 4. 工作区脏了怎么办

| 脏源 | 判据 | 处理 |
|---|---|---|
| **上一轮没做完** | `优化队列.md §1` 写着「进行中」，且脏文件正是它写的 | → 走 §5 |
| **后台生图** | `.gen-art.lock` 在，且脏的是 `assets/cards/manifest.json` / `*.png` | **不碰、也不提交**。提交时列**显式路径**，**永远不许 `git add -A` / `git add .`** |
| **用户手改** | 以上都不是，且改动看得出明确意图 | **不覆盖、不提交、不还原**。先看 `git log` 与文件内容，本轮绕开这些文件 |

⚠️ **`git add -A` 是这一节唯一的高危动作**：它会把后台生图正在写的 manifest、
用户的手改、上一轮的半成品一起卷进提交，事后极难拆干净。

---

## 5. 上一轮没做完（🔴 用户点名：先核实，再决定跳不跳）

> ⛔ **不许一句「上轮未完成，跳过」就收工。** 必须逐条回答下面 4 问，**并把答案写进台账**。

**第 1 问｜它卡在哪？**
具体到文件与命令，以及「半成品现在能不能跑」。例：`gen-art.py 改到一半，语法验过但没跑过`。

**第 2 问｜工作区还可用吗？**
- 门禁是否**双绿**？
- 有没有**半截的写盘**（改了一半的脚本 / 写了一半的 JSON）？

**第 3 问｜它真的影响本轮候选吗？**（**这一问就是用户说的「仔细检查」**）
按**四个面**判，不要凭「都是同一大类」就下结论：

| 关系 | 判定 |
|---|---|
| 同一文件 / 同一模块 | **影响**（改下去必冲突） |
| 同一机制 / 同一口径（例：都在动提示词拼装、都在动存档迁移） | **影响** |
| 只是同一大类，但文件与机制都不同（例：都是「生图相关」，一个动 `gen-art.py`、一个动 `check-cards.py`） | **不影响** |
| 完全不同的面 | **不影响** |

**第 4 问｜结论（三选一，写进台账）**

| 结论 | 何时用 |
|---|---|
| `接续做完` | 它是 A 类条目、只差收尾（门禁 / 文档 / 提交），且**本轮做它比开新条目更省** |
| `绕开它，做队列下一条` | 第 3 问判为**不影响** ⇒ **默认走这条** |
| `整轮跳过` | **只有**「工作区脏 **且** 门禁红」才允许。且台账必须写明：红在哪、为什么不能顺手修、下轮的先决条件是什么 |

**跳过的轮次不许只留一句结论** —— 下下轮的人要靠这段记录判断「这个坑还活着吗」。
台账里至少要能看出：**卡在哪个文件、下一步的第一个动作是什么**。

---

## 6. 收尾（缺一步都不算完成）

沿用 `docs/开发者文档.md` §18 的 5 步，**再加两条**：

1. 🔴 找它的**反向陈述**（哪一句话在说「它以前是那样」）
2. grep 常量 / 术语 / 文件名（含 `tools/` 与 `.html`）
3. 同步三处文档：`开发者文档.md` · `画风与颜色标准.md`（若涉及） · `GDD.md`
4. **门禁跟着改，并反向验证**：新增断言必须**先证明它会报红**（故意写坏 → 应报错 → 还原）
5. 记忆落盘：`.workbuddy/memory/YYYY-MM-DD.md` 追加；**必须记住的**写 `MEMORY.md`
6. **更新 `docs/优化队列.md`**：§1 当前状态（本轮完成 / 进行中 + 下一轮的起点）+ §4 台账**追加**一行
7. **一笔提交一个条目**：提交信息写清「做了什么 / 为什么 / 验证方式」

**验证口径**（数字每次都要用**实跑结果**覆盖，不许抄旧值）：

```bash
node tools/test.js     # → 619 项全过
node tools/verify.js   # → 0 错误 0 警告
```

**涉及 UI / 音频 / 画面的改动，必须再用真实浏览器跑一遍**（Node 单测看不到渲染与声音）：

```bash
python -m http.server 8765 --bind 127.0.0.1     # 起服务
playwright-cli open http://127.0.0.1:8765/index.html
# ……验证完，务必关掉服务（它会挂在后台任务列表里）
```

> 本项目的教训：**「测试全绿但画面是坏的」真的发生过**（拉扯输入通道那条：画布按住不收线、
> 松手监听没绑上，单测全过，玩家必断线）。所以碰 UI 就要真跑。

---

## 7. 禁止事项

- 不许改写 `docs/改进待办.md` 里**已有条目的「影响 / 建议」正文** ——
  完成时按该文件的惯例把 `- [ ]` 改成 `- [x]`，并在末尾**追加** `→ 已做（<hash>）：…` 行。
  发现原文写错了**不要就地改**：追加一条新条目说明更正（历史上就是这么做的）。
- 不许为了让门禁变绿而**放宽 / 删除 / 注释掉**断言。
  判定「断言本身写错了」需要单独留一笔：旧断言错在哪、新断言为什么对、怎么证明。
- 不许加**没有消费方**的导出（verify 第 ㉜ 节）。
- 不许把数值写进逻辑代码（一律进 `src/data/*.js`）。
- 不许连续两轮做同类**小**事凑工作量。
- 不许提交 `dist/`（已 gitignore）、`assets/cards/*.png`、`assets/cards/.gen-art.lock`。
- 不许在 `docs/` 里写会被门禁自指的示例（详见 §18 的「自指陷阱」）。

---

## 8. 需要用户拍板的条目

队列里标 `⛔需拍板` 的，**不要自动决定，也不要因此停工**：
跳过它取下一条，并在台账里写一句「等用户口径」。

判断标准：**两种做法观感 / 长期成本差别明显，且属于产品取舍（不是 bug）** ⇒ 标 ⛔。
典型的已积累项见 `docs/优化队列.md §3`。

## 9. 自主决策：**质量优先**（2026-10-08 用户口径）

> 用户原话：**「你做的决定要质量优先」**。
>
> 适用：规范允许自动化**自己拍**的事（即**不是**产品取舍的那些）。标 ⛔ 的产品取舍仍然要问用户。
> 这条不是「多做点」的同义词 —— 它约束的是**怎么在两个都能过关的方案之间选**。

### 9.1 什么叫质量优先（五条判据）

1. **选「同源一致」而不是「当下最省」** —— 宁可多改两个调用点，也要让**同一个事实只有一处真相**。
2. **选「规则说得清」而不是「这次能过」** —— 边界模糊时宁可把边界连同**反例**一起写死，
   也不留一句「看情况」。本项目已经因为「规则没写清楚」吃过亏（下面 9.3 的帧调度那条）。
3. **选「留证据」而不是「看起来对」** —— 新增断言**先证明它会报红**；新增能力**先想它的消费方**。
4. **不可逆性优先** —— 两案质量相当、但一案的返工成本更高时，选**可逆**的那个，并写明为什么。
5. **不许拿「影响低」当理由说假话** —— 影响低只说明**优先级**低，
   不说明文档里可以写一句不成立的「现状是 X」。

### 9.2 决策必须留痕（三处，缺一不算决策）

1. 产出物里（代码 / 文档）的**注释写明理由** —— 尤其是「为什么不选另一条路」；
2. `docs/优化队列.md` 台账**追加**一行；
3. 涉及口径的，**追加**进 `docs/改进待办.md`（只追加）。

### 9.3 已经拍定的边界（**别再反复摇摆**）

| 问题 | 结论 | 理由 |
|---|---|---|
| `requestAnimationFrame` / `cancelAnimationFrame` 算平台能力吗 | **算** —— 已收进 `sys.raf` / `sys.cancelRaf` | 小程序（非小游戏）页面里**没有**全局 raf，要换成 `canvas.requestAnimationFrame` |
| `setTimeout` / `setInterval` 算吗 | **不算** —— 业务代码可以直接用 | 任何宿主都有（连 Node 都有）；包一层只是多一层无意义的间接，还会**掩盖**「真正要换的只有帧调度」这件事 |
| 平台层拿不到某个能力时怎么办 | **兜底，不抛**；调用方**不再写「能力在不在」的守卫** | 例：`sys.raf` 退回 `setTimeout` 并**补上时间戳**（必须与 `sys.now()` 同源，否则主循环 dt 直接算炸）；调用方只保留「我自己的状态有没有在跑」这种守卫 |

> **这条边界的来历**：用户问「`requestAnimationFrame` / `setInterval` 要不要也收进平台层」，
> 并把决定权交给自动化。按 9.1 第 1、2 条拍定为**「收口帧调度、不收口通用计时器」** ——
> 收口一半看起来不整齐，但「整齐」不是目标，**规则能被执行**才是。
> 两条都收口会让 `verify` 多两条拦不住任何真问题的断言；两条都不收口则给小程序页面版留坑。
