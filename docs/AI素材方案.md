## 2. 先说清楚：换引擎为什么不是这次的答案

「简陋」拆成三层看：

| 层 | 现状 | 换 Godot/Unity 能改善吗 |
|---|---|---|
| ① 网格工艺 | 规则环形网格、鳍是单个三角形、无头部结构 | ❌ **完全不能** —— 引擎只是渲染器，喂给它的还是这套网格 |
| ② 着色 | 逐面平涂 + 边缘光 | ✅ 能 |
| ③ 引擎/工具链 | 手写 Canvas 2D | ✅ 能，代价 16000 行重来 |

**AI 出图恰好绕过①** —— 不需要我们手工建出好网格，直接拿图当素材用。
这就是为什么这条路能让画质一步到位。**前提是接受下面这个冲突。**

## 3. ⚠️ 必须解决的冲突：AI 出图 × 360° 旋转

**这是整条路线唯一的硬伤，必须先想清楚再动手。**

我们已经在规格里承诺了「图鉴详情页 360° 拖拽」。但扩散模型**画不出「同一条鱼转了 15°」**——
它每次都是重新画一条长得像的鱼。于是：

| 做法 | 后果 |
|---|---|
| 每个角度单独出图 | **拖动时鱼会变形、跳变**（头身比例、鳍的位置都会变）——一眼就穿帮 |
| 只出一个角度 | 没有 360°，退化成静态展示 |
| 用 AI 图当**贴图**贴在程序化网格上 | 360° 保住了，但网格还是简陋的那个 —— **画质提升有限** |

**结论：AI 出图与「真 360°」在技术上不兼容。** 只能二选一，或者分层：

- **保 360°** → 详情页继续用程序化 3D（画质受限），AI 图只能做卡面
- **保画质** → 详情页改用 AI 大图，**取消 360° 旋转**，改为静态展示 + 轻微浮动 / 视差

> 我的判断：**360° 是可玩性里最弱的一环，画质是最强的一环。** 玩家在图鉴里停留的时间
> 主要花在「这条鱼好不好看、我要不要收集它」，不在「转着看」。所以我倾向**牺牲 360°**。
> 但这个决定影响你在会上怎么讲这个产品的卖点，得你来定。

## 4. 体积预算（⚠️ 口径已变：不再是约束）

> 「素材放到专属的地方**以后上云端，不直接放到小程序里**，所以不会超过大小。

**所以体积这一节降级为「参考信息」**，不再是设计约束。保留推算表是因为它解释了

## 6. 落地：管线由三个工具组成（2026-10-07 已跑通并验收）

| 工具 | 职责 | 解释器 |
|---|---|---|
| `tools/gen-art.py` | 出**母版**（每条鱼一张）。提示词由 `fish.js` 字段拼装，可复现 | managed python 3.13.12 |
| `tools/paint-card.py` | 从母版派生 **5 档颜色**（灰度 → 伽马归一 → 双色渐变映射 → 抠图 → 构图归一） | **系统 conda**（有 PIL） |
| `tools/check-cards.py` | **自动验收**：背景一致 / 贴边裁切 / 主体占比 | 同 conda |

**核心分工一句话：AI 管形态与光影，程序管颜色与构图。**

- 为什么颜色不交给 AI：文生图**控不住精确颜色**（实测三条灰蓝色的鱼被画成同一个浅蓝）。
  程序化调色还能带来一个额外好处：**5 档共用一张母版 → 逐像素同构图，切色不跳变**。
- 颜色口径的**唯一来源是 `src/render/fishpaint.js` 的 `palette()`** —— python 借 `node -e` 调用，
  **不重新实现**（同口径写两遍必然分家，这是本项目反复踩过的坑型）。
- 形态区分度来自三层：**名字族**（中文科属字 → 形态，覆盖 ~80%）→ `body_ratio` 兜底 →
  科属花纹倾向（**查证优先，查不到留空；随机已删除**，见开发者文档 §17.5）。

**规模**：每条 5 次出图（母版 + 4 档；原色档是母版的抠图，不额外出图）
→ 生成 **1810 次**、成品 **2172 张文件**（`<id>.png` + 5 档透明图）；纯出图约 **6.4 小时**（单张约 55s，cfg=3.0 每步跑两次前向），
可分批过夜跑。分批评审节奏见 `docs/生图清单.md`。

**还没做的**：`G.Assets` 素材表（游戏侧接入）—— 见下一节。

### 8.2 多视角：能减工作量，但取法要对（2026-10-08 咨询结论）

- **视角按「语义」选，不按「角度」选**：侧视（母版）/ 俯视 / 正面。**不要连续角度** ——
  否则又回到「每条鱼都要重画且角度必须精确」的老坑。
  **差异大反而是优点**：AI 重画必然身份漂移，差异大时读成「换了个视角」，差异小时读成「画崩了」。
  ⇒ §3 那句「画不出连续的 15°」**不等于**「画不出相隔 90° 的两张」。
- **视角之间用交叉淡入（cross-fade），不做连续拖拽**：把过渡做成刻意的切换动作，玩家不会逐帧比对。
- **能程序白送的视角不要花 AI 的钱**：水平镜像（免费的另一侧）、±8° 轻微倾斜；
  且 **5 档色共用母版** ⇒ 视角图**只需按母版出，不需按 5 档出**。
- **⚠️ 第二视角必须走图生图锚定母版**（纯文生图重画必然换一条鱼）。两条路：
  ① 方舟 `ark_image.py` 的图生图**已跑通**，最省事；② ComfyUI 那条要另下 Edit 模型，**尚未接通**。
- **成本（按实测 62 s/张）**：全量加 1 个第二视角 = 362 张 ≈ 6.2 h；
  **只给传说档 27 条 = 27 张 ≈ 28 min** ⇒ **建议：图鉴默认侧视 1 张，第二视角只给传说档做。**

### 8.3 贴图尺寸：两层必须解耦（2026-10-08 咨询结论）

| 议题 | 结论 |
|---|---|
| 画布**像素尺寸** | **必须统一**（建议 2:1，如 1024×512）。按鱼大小输出不同像素尺寸会让图鉴网格大小跳变、布局对不齐、素材表复杂化 |
| 「大鱼显大、小鱼显小」 | 由**渲染端**用 `minKg`/`maxKg` 映射 **0.6~1.0 显示系数**控制，**不是**由图片像素尺寸控制 ⇒ 改口径不用重出图 |
| 「后期统一调整」 | ✅ 应该做成**独立的归一化后处理 pass**，而不是出图时就把大小烘死 |

**后处理 pass 口径（现有 692 张可直接批处理，不用重出图）：**
- 源 1152×768（3:2）→ **保持高度、水平透明补边**到 1536×768 → 降采样到 1024×512（2:1）
  —— **是补边不是裁切**（鱼的长轴水平，裁高会切掉背鳍 / 腹鳍）
- 同一个 pass 顺手做：列表档（+ 锐化）、边缘 halo 去污染、bbox / 长轴 / 重心落盘

**两处必须先定的口径：**
1. `paint-card.py` 的「构图归一」目标 = **统一长轴占比**（如长轴 = 画布宽 82%），
   大小关系 100% 交给渲染系数；**不要**归一到「真实比例」（小鱼图会浪费大量像素、且更糊）
2. 展示位长宽比：详情 380×190 = **2:1 ✅**；列表 260×112 = **2.32:1 ❌** → 建议改 **260×130**
